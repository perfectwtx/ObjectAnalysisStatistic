# Core 项目重构实施方案

> 状态：方案定稿待执行 ｜ 基线：HEAD `c22cfdf`；用户已开始的 `Abstractions/` 端口改造作为 W2 起点
> 原则：**破坏性改动是明确目标，不是风险**——三宿主（CLI/API/Web）全部基于 Core 重写，对外契约（CLI 选项与退出码、API 响应形状、Web 行为）允许重新设计，语义化版本升至 v2.0。
> 仅保留三条过程约束：每阶段独立提交、全量测试守门、单一会话执行构建

## 一、现状诊断（7 项，全部在当前代码中定位实证）

| # | 问题 | 实证 | 后果 |
|---|------|------|------|
| 1 | 巨型静态编排入口 | `AnalysisRunner.cs` 1324 行；`RunCore`（L78–522）一个方法包含校验/预检/续跑/解析分发/快照/报告/4 类门禁/审计 | 加功能只能改这一个方法；无法单测任一阶段 |
| 2 | 静态可变状态 | `AnalysisRunner.cs` L22–25 `[ThreadStatic] _lastQuantileSketches/_lastDistinctSketches`、L41 `s_activeMemoryBudget`（L218 写、L847/853 读） | 测试被迫串行（`AnalysisRunnerSequentialGroup`）；并行实例化不可能 |
| 3 | 核心库硬依赖控制台 UI | `AnsiConsole.*` 在 Core 共 **145+ 调用点**（AnalysisRunner 73、ConsoleReporter 50、SchemaDiffer 12、DistributionDiffer 10、ReportExporter/Quality/Pii 各 2–3） | API/Web 复用 Core 被迫携带 Spectre.Console；进度/日志无法按宿主替换 |
| 4 | 统计与分类逻辑内联 | `ObjectAnalyzer.cs` 1191 行：值分类、语义正则、Welford、直方图、PII 提示匹配等全部内联 | 加统计项要在引擎巨石内找位置；无法单测 |
| 5 | 管线三处重复 | parse→transform→sample→analyze 编排存在于 CLI `AnalysisRunner`、Api `AnalysisCore.AnalyzeFile`、Web `Home.razor` 内联 | 两个已知缺陷（见下）要在三处修；行为分叉 |
| 6 | 规则与选项双轨 | 规则 `runtime` 节点为 JsonObject，`RulesToOptionsConverter` 单遍合并 + `RulesLint` 白名单兜底 | 加一个选项要同步 Converter、Lint 白名单两处（已加对拍锁定，仍属双维护） |
| 7 | 扩展点靠分支 | 报告格式按扩展名 if/else 链（`ReportExporter.Save`）、四类门禁退出码 3/4/5/6 硬编码 | 新增导出格式/门禁必须改 Core |

**伴随缺陷（阶段二修复后自动消解）**：
- `filter` + `flatten:true` 同配时字段级质量检查被跳过；
- `valueParsers` 配置即强制 excel-json 解析（普通 JSON 报字典错误）；
- `maxValues` 只影响控制台展示，API/Web 结果 JSON 不受控——语义易误解。

**已确认干净、无需再动的**：15 个选项子组（零死属性）、规则模型属性（零沉默键）、Converter 与 RulesLint 白名单一致、Api Contracts/Endpoints 分层。

## 二、目标架构

```
宿主（CLI / API / Web）各自构造 ──► AnalysisOptions（IR，15 子组）+ AnalysisRules（标准）
                                        │
                                        ▼
                     AnalysisPipeline.Execute(...)        ← W1：唯一分析管线
                       │  Parse → Transform → Sample → Analyze
                       │  （缺陷 1/2 在此一次修死）
                       ▼
                     AnalysisRunContext（实例）           ← W3：预算/草图/取消全部入上下文
                       │  Console / Progress / Presenter  ← W2：宿主端口（Abstractions/）
                       ▼
                     报告注册表 ──► 按格式分发             ← W4：注册表替代 if/else
                     门禁注册表 ──► 逐条检查，退出码是数据
```

一句话：**"一条大静态过程" → "一条可装配的管道 + 三张注册表 + 一组宿主端口"**。新增格式/门禁/统计项 = 注册一个实现，不再改核心。

## 三、工作流分解

### W1 统一分析管线【修复缺陷 1/2 的唯一落点】

- 新建 `Analysis/Pipeline/AnalysisPipeline`：`Execute(AnalysisOptions, AnalysisRules?, AnalysisServices, CancellationToken) → AnalysisResult`。
- 内部顺序：格式解析（`ParseByFormat`）→ 投影（jsonPath）→ 字段选择/转换/过滤（`FieldTransformProcessor`）→ 采样 → `ObjectAnalyzer.Analyze`。
- **缺陷修复落点**：`valueParsers` 仅在输入格式确为 excel-json 时生效（不再强制改写格式）；字段质量检查固定在「展平+过滤后」的对象流上执行。
- 宿主改造：CLI `RunCore` 的解析分发段、Api `AnalysisCore.AnalyzeFile`（删除）、Web `Home.razor` 内联管道（删除）全部改为调用 Pipeline；Web 的进度文本经 `IProgress` 注入。
- 验收：同输入在 CLI/API/Web 产出**逐字节一致**的结果 JSON；新增"三宿主行为一致性"测试。

### W2 宿主端口抽象（完成已开始的 Abstractions 改造）

- 已有：`IAnalysisConsole` / `IProgressReporter` / `IResultPresenter` / `AnalysisServices` / 静默实现 / `MarkupText`。
- 补齐：Core 内 145+ 处 `AnsiConsole.*` 分三类迁移——
  1. 过程消息（开始/警告/保存提示）→ `services.Console`；
  2. `ConsoleReporter`（50 处 Spectre 富渲染）→ 整体变为 CLI 侧 `IAnalysisConsole` 的**实现**，Core 通过接口回调；
  3. `MemoryBudget` 警告 → 完成 WIP（`_console`/`_consoleField` 双字段收敛为单字段 + `SetConsole`）。
- 验收：`ObjectAnalyzer.Core.csproj` 移除 Spectre.Console 包引用后编译通过；CLI 输出**允许视觉重设计**（现代化，不做等价对照）。

### W3 静态可变状态实例化

- 新建 `AnalysisRunContext`（实例对象）：`MemoryBudget`、两级草图缓存、`IncrementalContext`、取消令牌——随 Pipeline 构造传入，贯穿各阶段。
- 删除 `AnalysisRunner` 的 `[ThreadStatic]` 字段与 `s_activeMemoryBudget`。
- 验收：删除 `AnalysisRunnerSequentialGroup` 后全部测试仍可并行通过。

### W4 导出与门禁注册表

- `IResultExporter { string Format; void Save(result, path); }` 注册表替代扩展名 if/else 链；`ReportExporter` 变为路由器。
- `IQualityGate { GateVerdict Check(AnalysisResult, AnalysisOptions); }` 列表替代 if/else 链；退出码 3/4/5/6 成为门禁的属性（数据），不再是核心硬编码。
- 新增导出格式/门禁 = 注册新实现。

### W5 引擎剖析策略化【独立后续阶段，本轮可选】

- `ObjectAnalyzer.cs` 内的字段指标贡献逻辑拆为 `IFieldMetricContributor` 列表。规模大、收益中等——单独立项，不阻塞本方案其余部分。

### W8 三宿主基于 Core 重写【破坏性改动的主体】

宿主不再是"适配旧 Core 的胶水"，而是基于新接口（Pipeline + AnalysisServices + 注册表）的**薄适配层**：

- **CLI**：选项面按功能重新分组与命名（顺带解决 `maxValues` 语义歧义——拆分为展示数量与分析上限两个正交选项）；`RunAnalysis` 改走 Pipeline + AnalysisServices；输出现代化（结构化消息 + 进度渲染由端口注入）。
- **API**：契约按 React 前端所需重新设计——同步分析、异步任务（提交/轮询/取消，扩展现有 AsyncAnalyzeEndpoints）、进度推送（SSE）；响应形状直接对齐前端五块页面（概览统计/字段明细/深度分析/数据预览/质量报告）。
- **Web (Blazor)**：删除内联管线与 `AnalysisState` 选项混装，分析流改走 Pipeline + AnalysisServices；页面数据消费与 React 同构的 API 契约（Blazor 与 React 双前端共用同一 API）。
- 对外契约变化集中记录于 CHANGELOG（v2.0 破坏性变更清单 + 迁移说明）；React 前端本就在开发中，同步适配成本最低。

### W6 规则单轨收口

- `RulesLint` 白名单改为**从 `RulesToOptionsConverter` 的已知键集合自动推导**（对拍测试锁定），消除双维护。
- `runtime` 保持 JsonObject（灵活性优先）；强类型化评估另立结论，本轮不做。

### W7 编排拆分

- `RunCore`（440 行）按阶段拆为 partial：`Preflight` / `Resume` / `ParseDispatch` / `ReportAndGates`。行为以现有测试锁定，允许输出文案变化。

## 五、版本与迁移策略

- 对外契约（CLI 选项/退出码、API 响应形状）属破坏性变更：语义化版本升至 **v2.0**，CHANGELOG 单列「破坏性变更清单 + 迁移说明」。
- React 前端与本 API 同仓库节奏开发，契约重设计与其同步落地（成本最低窗口）。
- 旧 CLI 若有脚本依赖：v1.x 维护分支冻结保留，仅修严重缺陷。

## 六、风险与回滚

| 风险 | 缓解 |
|------|------|
| 与并行会话构建竞争 | 重构期间单侧执行构建；`csc.exe` 竞争已实测会崩溃 |
| `AnalyzeDetailed` 草图消费方（Web 分布漂移）断链 | W3 迁移时草图经 RunContext 显式传递，Web 调用点同步改造 |
| 三宿主重写工作量超预期 | W8 拆为三段独立交付（CLI → API → Web），任一段完成即是稳定态 |
| 大 diff 审查困难 | 每阶段独立提交；结构搬移与缺陷修复分开提交 |

## 七、明确不做的事

- 统计算法本体不动（Welford / HLL / t-digest / 语义正则）；
- `FieldTransformProcessor`（765 行）不拆——职责单一（按规则处理对象流），拆分收益低；
- Api 的异步分析/预检/取消**架构**保持（并行会话新交付，运行良好），契约形状在 W8 中允许重新设计；
- Web `AnalysisState`（UI 状态 + 选项混装）拆分并入 W8 的 Web 接线改造；
- `runtime` 节点强类型化另做评估（当前 JsonObject + RulesLint 已够用）。
