# ObjectAnalyzer 架构重构与平台化设计

> 当前状态：已完成并进入平台化迭代阶段。
>
> 本文由早期“Core 重构实施方案”更新为当前实际架构说明。历史方案中的“待执行”描述不再作为项目状态依据。

## 1. 重构目标

ObjectAnalyzer 最初以 `AnalysisRunner` 为中心，CLI、API、Web 分别编排解析、转换、过滤、采样和分析流程，导致核心逻辑重复、宿主行为容易分叉、扩展成本较高。

本轮重构的目标是建立一个稳定的分析内核，并在此基础上逐步平台化：

```text
CLI / API / Web / Scheduler
          │
          ▼
   Analysis Platform
          │
          ▼
   AnalysisPipeline
          │
          ▼
     AnalysisResult
          │
     ┌────┴────┐
     ▼         ▼
Quality     Complex
Metrics     Analysis
  /Issues      │
     │         │
     └────┬────┘
          ▼
    History Store
          │
          ▼
 Quality Dashboard
          │
          ▼
   Alert / Webhook
```

## 2. 当前架构

### 2.1 Core

`src/ObjectAnalyzer.Core` 是唯一分析事实来源，负责：

- 输入解析
- JSONPath 投影
- 字段选择
- 值转换
- 过滤
- 采样
- 字段统计
- 数据质量检查
- Schema 分析
- 深度分析
- 报告导出
- PII 策略与审计能力

Core 不依赖 Web UI，也不承担宿主生命周期管理。

### 2.2 AnalysisPipeline

所有标准分析统一经过：

```text
Parse
 ↓
Root/Record JSONPath
 ↓
Field Selection
 ↓
Transform
 ↓
Filter
 ↓
Sampling
 ↓
Analysis
 ↓
AnalysisResult
```

运行期状态通过 `AnalysisRunContext` 传递，包括内存预算、续跑位置、进度桥接、预览捕获和执行观察器。

### 2.3 Host Abstraction

CLI、API、Web 通过宿主端口与 Core 交互。

核心接口包括：

- `IAnalysisConsole`
- `IProgressReporter`
- `IResultPresenter`
- `AnalysisServices`

因此核心分析逻辑不需要知道具体 UI 技术。

## 3. 平台化层

平台化能力位于 `ObjectAnalyzer.Platform`，主要职责不是重新实现分析，而是管理“分析任务以及分析结果的生命周期”。

### AnalysisJob

每次分析对应一个 Job：

```text
Pending → Running → Succeeded
                 ├→ Failed
                 └→ Cancelled
```

Job 保存来源、耗时、对象数、字段数、质量分、Issue 数以及复杂结果 JSON。

### AnalysisExecutionCoordinator

统一封装 Job 生命周期：

```text
StartAsync
   ↓
Execute
   ├── CompleteAsync
   ├── FailAsync
   └── CancelAsync
```

未来 Scheduler、API、Web 等入口均应通过该服务执行平台任务。

## 4. 数据质量模型

质量指标被标准化为五个维度：

| 指标 | 权重 |
|---|---:|
| Completeness | 30% |
| Validity | 30% |
| Uniqueness | 15% |
| Consistency | 15% |
| AnomalyControl | 10% |

质量快照、字段质量快照和质量 Issue 使用结构化模型保存。

## 5. History Store

当前实现使用 SQLite，抽象为 `IAnalysisHistoryStore`。

主要数据：

```text
analysis_jobs
quality_snapshots
field_quality_snapshots
quality_issues
```

设计上通过接口隔离数据库实现，后续可以增加 PostgreSQL，而无需改变 Dashboard 和业务服务。

## 6. ResultJson 的定位

平台没有把所有分析结果都拆成数据库表，而采用“双层模型”：

### 结构化层

用于频繁查询、趋势、告警：

- QualitySnapshot
- FieldQualitySnapshot
- QualityIssue

### 扩展层

用于复杂或变化频繁的分析结果：

- SchemaDiff
- CorrelationMatrix
- DistributionDiff
- FuzzyDuplicates
- TimeSeries

这样可以在查询效率和扩展成本之间保持平衡。

## 7. Web 平台

Web 页面只负责展示平台服务返回的数据。

当前主要页面：

- `/quality`：Quality Dashboard
- `/quality/trend`：质量趋势
- `/quality/fields`：字段详情
- `/quality/regression`：质量回归
- `/quality/schema-impact`：Schema 影响
- `/quality/relationships`：字段关联
- `/quality/recommendations`：治理建议
- `/issues`：Issue Center
- `/alert-rules`：告警规则

新增页面原则：优先查询 Platform 层标准化数据，不在 Razor 页面重复实现质量计算。

## 8. 告警与 Webhook

告警条件由 `AlertRule` 表达，目前支持：

- 质量分低于阈值
- 完整性低于阈值
- 质量回退
- 严重质量问题
- Schema 破坏性变化
- 分布漂移

触发后写入 Webhook Outbox。

```text
Analysis
   ↓
AlertEvaluator
   ↓
WebhookDelivery
   ↓
Outbox
   ↓
Background Worker
   ↓
HTTP Webhook
```

Worker 负责失败重试和指数退避，分析任务不直接依赖外部 Webhook 服务。

## 9. 测试策略

当前测试分为：

- Core 单元 / 集成测试
- API 集成测试
- Web 冒烟测试
- Platform 服务测试

重点保证：

1. 相同输入经过统一 Pipeline 后结果一致。
2. Job 生命周期正确持久化。
3. Quality Snapshot 与 AnalysisResult 口径一致。
4. Webhook 失败不会导致分析任务失败。
5. 取消任务能够持久化为 Cancelled。

## 11. 架构约束

- Core 不依赖 UI。
- 页面不复制核心分析算法。
- 平台服务不绕过 AnalysisPipeline。
- 标准指标优先结构化存储。
- 复杂结果允许 JSON 扩展。
- 外部通知必须经过 Outbox。
- 新增能力必须考虑 CLI / API / Web / Scheduler 的复用。
