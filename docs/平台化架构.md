# ObjectAnalyzer 数据质量平台化架构

## 1. 定位

ObjectAnalyzer 不再只是一次性的对象字段统计工具，而是以统一分析引擎为核心的数据质量分析平台。

平台同时支持：

- CLI：本地分析、脚本和 CI 门禁
- Mini API：提供 HTTP 分析能力
- Blazor Web：质量分析与运营界面
- 后台任务：统一分析 Job 生命周期
- SQLite：本地历史数据存储
- Webhook：质量告警异步投递

## 3. 核心领域对象

### AnalysisJob

表示一次完整的分析任务，记录：

- SourceName / SourceType
- Status
- StartedAtUtc / CompletedAtUtc
- DurationMs
- TotalObjects / FieldCount
- QualityScore
- IssueCount
- ErrorMessage
- ResultJson

任务状态：Pending、Running、Succeeded、Failed、Cancelled。

### QualitySnapshot

表示一次分析产生的标准化质量快照。

质量评分由五个维度组成：

| 指标 | 权重 |
|---|---:|
| Completeness | 30% |
| Validity | 30% |
| Uniqueness | 15% |
| Consistency | 15% |
| AnomalyControl | 10% |

最终生成 OverallScore。

### FieldQualitySnapshot

保存字段级质量指标：

- Coverage
- NullRate
- Uniqueness
- OutlierRatio

用于字段详情、趋势和后续质量治理。

### QualityIssue

统一表达质量问题：

- FieldName
- Check
- Count
- Message

包括必填、枚举、范围、唯一性、Pattern、Null Rate、异常值以及重复对象组等问题。

## 4. 持久化策略

平台采用“结构化指标 + 原始复杂结果”双层模型。

### 结构化数据

以下内容进入 History Store：

- AnalysisJob
- QualitySnapshot
- FieldQualitySnapshot
- QualityIssue

它们承担趋势、查询、Dashboard 和告警的主要数据来源。

### ResultJson

复杂且变化较快的分析结果继续保存在 AnalysisJob.ResultJson，例如：

- SchemaDiff
- CorrelationMatrix
- DistributionDiff
- FuzzyDuplicates
- TimeSeries

这样可以避免为了每一种分析结果不断修改数据库结构。

## 5. 分析任务生命周期

所有平台化分析优先通过 `AnalysisExecutionCoordinator` 执行：

```text
Start
  ↓
Running
  ├── Success → Complete → Save Snapshot / Issues → Evaluate Alert
  ├── Error   → Failed  → Save Error
  └── Cancel  → Cancelled
```

这样 CLI、API、Web 和未来的 Scheduler 可以共享同一套任务生命周期。

## 6. 告警架构

告警规则由 `AlertRule` 定义，可以基于：

- QualityScoreBelow
- CompletenessBelow
- QualityRegressionBelow
- CriticalIssue
- BreakingSchemaChange
- DistributionDriftAbove

触发后进入 Webhook Outbox，而不是直接在分析线程中发送 HTTP 请求。

### Outbox 优点

- 分析任务不依赖 Webhook 服务可用性
- 网络失败可以自动重试
- 支持指数退避
- 达到最大尝试次数后记录最终失败
- 后续可以扩展更多通知渠道

## 7. Web 页面职责

Web 页面只负责展示和交互，不重新实现分析核心逻辑。

当前平台页面：

| 页面 | 路由 | 职责 |
|---|---|---|
| Quality Dashboard | `/quality` | 质量总览与 Top Issues |
| Quality Trend | `/quality/trend` | 历史质量趋势 |
| Field Detail | `/quality/fields` | 字段质量详情 |
| Quality Regression | `/quality/regression` | 前后版本质量变化 |
| Schema Impact | `/quality/schema-impact` | Schema 变化与影响 |
| Relationships | `/quality/relationships` | 字段相关性 |
| Recommendations | `/quality/recommendations` | 治理建议 |
| Issue Center | `/issues` | 质量问题集中查看 |
| Alert Rules | `/alert-rules` | 告警规则配置 |

## 8. 扩展方向

### 数据源

未来通过 DataSource 抽象统一：

```text
FileDataSource
DatabaseDataSource
ApiDataSource
ObjectStorageDataSource
```

### 调度

```text
Scheduler
   ↓
AnalysisJob
   ↓
AnalysisExecutionCoordinator
```

调度器不直接调用 AnalysisPipeline，避免任务生命周期再次分散。

### 存储

当前 SQLite 适合单机和开发环境，后续可以增加 PostgreSQL 实现，而不改变上层查询接口。

### 通知

Webhook 是第一种通知渠道，后续可以增加：

- Email
- 企业微信
- 钉钉
- Slack
- Teams

通知渠道应复用 Outbox，而不是各自实现重试机制。

## 9. 设计原则

1. **一次分析，一个 Job。**
2. **一个核心分析管线。**
3. **质量指标结构化存储。**
4. **复杂结果允许 JSON 扩展。**
5. **分析、持久化、展示、通知职责分离。**
6. **通知必须异步化。**
7. **CLI / API / Web / Scheduler 都应复用平台服务。**
8. **新能力优先增加领域服务或扩展点，不继续把业务逻辑堆进页面。**
