# Core 项目优化清单

更新日期：2026-10-18

范围：`src/ObjectAnalyzer.Core` 及其必要的宿主适配和回归测试。

目标是升级代码结构，提高复用性、扩展性和统计结果的可靠性。允许调整公开接口、序列化契约和项目边界；涉及破坏性改动时，应明确版本和迁移方式。

本文是 Core 的技术优化清单，与产品功能路线图分开维护。第一、二、三、四项已实施，其余为待实施建议；后续接口名称仍是设计草案。

## 总览与建议顺序

| 顺序 | 优化项 | 状态 | 主要收益 |
|---|---|---|---|
| 1 | 建立统一的值类型和字段路径模型 | 已完成并推送 | 消除类型身份和路径歧义，统一基础数据契约 |
| 2 | 分离计算状态、分析结果和持久化快照 | 已实施 | 统一全量、并行、增量分析的统计语义 |
| 3 | 建立可组合的分析器与规则执行机制 | 已实施 | 新增统计和规则时减少对主引擎的修改 |
| 4 | 改造执行管线，移除全局运行服务 | 已实施 | 支持多任务隔离，统一取消、进度和生命周期 |
| 5 | 统一数据源与解析器契约 | 待实施 | 复用文件、数据库、流输入，明确各格式能力 |
| 6 | 明确流式处理和内存预算 | 待实施 | 控制大数据量及高基数字段下的资源占用 |
| 7 | 建立统一的结果投影与脱敏出口 | 待实施 | 避免输出漏字段，覆盖所有携带原始值的结果 |
| 8 | 重构 Schema 推断与导出模型 | 待实施 | 让各语言和协议导出共享同一份结构推断 |
| 9 | 拆分计算内核、基础设施和平台业务 | 待实施 | 减少核心依赖，使算法可单独复用和发布 |
| 10 | 建立统计契约测试与性能基线 | 待实施，随各项推进 | 持续验证正确性、并发一致性和资源开销 |

前四项已完成，建议继续第 5 项，再推进内存预算、输入输出扩展和物理项目拆分。第 7 项中的原始值出口检查可以提前进行；第 10 项应贯穿整个重构过程。

## 1. 建立统一的值类型和字段路径模型

**状态：已完成。** 提交：`bff7354`，已推送至 `origin/main`。

### 已解决的问题

- 过去以显示字符串表达频次身份，数字 `1`、字符串 `"1"` 等值存在混淆风险。
- 点号字段名、数组索引、空字段名缺少统一表达，展平和路径匹配容易出现歧义。
- 解析、转换、去重和导出中存在重复的值转换逻辑。

### 已落地的改动

- `RecordValue`：不可变值模型，统一类型身份、精确数字编码、对象和数组的规范化。
- `FieldPath`：按属性段与数组索引段表达路径，提供解析、父路径、结构化前缀判断。
- `RecordNormalizer`：集中处理对象归一化和展平。
- 频次使用 `Dictionary<RecordValue, long>`；溢出数量通过 `OtherValueCount` 单独返回。
- 接入分析、解析、规则、过滤、预检、Schema、血缘以及必要的展示适配。
- 分析 checkpoint 升级至 v2，Schema 和分布快照升级至 2.0。

### 边界与验证

值身份保留数值精度；均值、分位数等算法仍使用 double。本项保留旧字典分析入口作为适配器，后续可继续将引擎内部迁移到类型化记录。

完整解决方案 Release 构建通过，零警告、零错误。Core 测试 666/668 通过，剩余两项为改动前已有的 SQLite 临时文件锁失败；API 125 项、Web 74 项全部通过。

接口与迁移说明见 [Core 值模型与字段路径](core-value-model.md)。旧版快照和无类型频次无法可靠自动恢复，需要重新分析数据源。

## 2. 分离计算状态、分析结果和持久化快照

**状态：已实施。**

落地 `AnalysisAccumulator`、独立字段计数和指标状态、状态 DTO 与 v3 检查点；移除报告模型的 `MergeFrom()`。统一全量、并行和增量合并，补充有效样本数、草图、跨批次去重、物理行游标和输入校验。CLI 与 Web 已同步适配。

当前支持基础统计和时间序列状态的恢复；尚无持久化协议的高级收集器明确拒绝续算。位置续跑先支持未压缩 JSONL，其他格式等待输入游标协议。结果 DTO 保留宿主适配所需的 setter，但不再参与数学合并。详见 [计算状态、结果与快照](core-analysis-state.md)。

以下保留该项的问题与验收依据。

### 原有问题

`ObjectAnalyzer` 同时负责逐条统计、线程局部状态、合并和结果收尾；`FieldStatistic` 既承载展示结果，又通过 `MergeFrom` 承担增量计算。

从最终结果反推计算状态会丢失信息。例如：

- 数值均值和方差合并需要有效数值样本数，不能直接使用包含 null、字符串等值的字段总出现次数。
- 分位数不能通过两份最终分位数正确合并。
- 去重数不能通过两个最终计数取最大值完成集合并集计算。
- 平均长度也需要自己的有效样本数和长度总和。

### 建议改造

- 引入独立的 `AnalysisAccumulator`、`FieldAccumulator`，保存计数、数值样本数、M2、长度总和及可合并草图。
- 统一 `Observe(record)`、`Merge(state)`、`Complete()` 三个操作。
- 全量、并行分块和增量分析共用同一种状态合并实现。
- `AnalysisResult`、`FieldStatistic` 作为最终结果模型，逐步改为只读快照。
- checkpoint 保存可恢复的计算状态，并记录版本、算法配置、输入位置和恢复所需信息。
- 将“历史结果对比”和“继续累计分析”明确为不同操作。

### 验收标准

同一数据集一次分析、分块合并和 checkpoint 恢复后的结果一致；近似统计在明确的误差范围内一致。覆盖混合类型、缺失字段、null、单样本、空分块、截断频次和高基数场景。无法恢复的旧结果应明确拒绝增量续算。

## 3. 建立可组合的分析器与规则执行机制

**状态：已实施。**

内置数值、文本语义、日期、唯一性和逐值规则组件已通过不可变注册集合组合。新增字段分析器、逐值规则和结果级规则均可注册接入，支持组件状态的合并与恢复。规则在读取前编译，pattern 和枚举违规按完整出现次数累计，展示样本有界。

旧内部状态 `analysis-state/v1` 需重新分析；外层检查点仍为 v3。接口、示例、计数与恢复契约见 [可组合分析器与规则执行](core-composable-analysis.md)。现有跨记录高级收集器的恢复限制仍适用。

以下保留该项的问题与验收依据。

### 当前问题

数值、日期、语义识别、去重和深度分析集中在主引擎；增加一项能力容易同时修改多段初始化、观察、合并和收尾逻辑。部分质量检查在收尾阶段依赖已截断的频次表，完整性受展示容量影响。

### 建议改造

- 将数值统计、日期统计、唯一性、语义识别等拆成独立组件，按配置组合执行。
- 组件共享第 2 项的状态协议，显式声明输入类型、状态、合并和输出方式。
- 规则先编译为执行计划，缓存路径、枚举集合和正则等准备工作。
- 逐值约束在观察阶段累计违规总数，单独保留有界样本；数据集约束在收尾执行。
- 区分违规出现次数、不同违规值数量和展示样本数量。
- 规则表达式、正则缓存和样本集合设置明确的生命周期与容量。

### 验收标准

新增一个统计组件或规则时，可以通过注册接入；频次截断后规则违规计数仍正确。禁用能力后不分配对应状态，不执行对应计算。

## 4. 改造执行管线，移除全局运行服务

**状态：已实施。**

新增实例化 `AnalysisExecutor`、不可变配置快照 `AnalysisExecutionPlan` 和每次运行独立的内部会话；删除 `AnalysisServices.Current/Use`，CLI 与 Desktop 通过 `AnalysisCommandRunner` 显式接入宿主端口，API/Web 使用实例执行器。静态入口保留为静默适配器。

统一结构化阶段、诊断、进度与终止事件；观察器异常隔离并有界保存，取消覆盖枚举、JSONL 物理行、并行记录和模糊聚类。所有格式在转换、过滤后统一采样，record-path 改为惰性投影。详见 [执行管线与运行隔离](core-execution-pipeline.md)。

以下保留原有问题与验收依据。

### 原有问题

`AnalysisPipeline` 已提供共享入口，但仍直接读取 `AnalysisServices.Current`，并包含带控制台样式的输出。宿主在进程级设置运行服务，会限制独立配置多个分析任务的能力。

### 建议改造

- 以实例化的 `AnalysisEngine` 或 `AnalysisExecutor` 接收依赖，每次运行使用独立上下文。
- 统一阶段：输入、投影、转换、过滤、采样、观察、收尾。
- 输出结构化阶段事件、进度和诊断信息，由宿主负责文字、颜色与界面呈现。
- 建立不可变执行配置，运行前完成校验和能力检查。
- 统一取消检查、异常分类和生命周期事件语义，明确观察者异常是否影响主任务。
- 静态入口可保留为简单适配层，核心计算不再依赖可变全局服务。

### 验收标准

两个任务可在同一进程使用不同进度订阅者和配置并发运行，事件互不串扰。取消时释放输入资源，并且只发出一次终止事件。

## 5. 统一数据源与解析器契约

### 当前问题

文件解析、数据库直连和 JSONPath 投影具有不同入口；解析器注册集中在静态列表。各格式在流式能力、采样、展平、取消和错误定位方面需要更明确的契约。

### 建议改造

- 建立数据源描述与读取接口，支持路径、流、数据库和调用方提供的记录序列。
- 解析出口统一为类型化记录，避免反复经过 `object?` 和 JSON 转换。
- 通过注册表添加解析器和格式检测器，支持宿主注入。
- 显式声明格式能力：是否流式、能否恢复位置、是否支持采样、是否需要整体物化。
- 明确采样所在阶段，避免各入口重复采样或采用不同口径。
- 诊断携带源位置，例如行号、工作表、列名或记录序号；支持明确的遇错停止与跳过策略。
- 对可异步读取的数据源提供异步枚举和取消支持。

### 验收标准

等价输入通过各适配器后具有一致的值与路径语义。增加格式无需修改主分析器。提前停止枚举、取消或异常均能释放文件、解压流和数据库读取器。

## 6. 明确流式处理和内存预算

### 当前问题

管线在模糊去重和分布快照等分支中会物化记录；字段频次之外，重复对象、诊断样本和深度分析也需要独立的资源限制。接口返回 `IEnumerable` 并不意味着全过程使用固定内存。

### 建议改造

- 在执行计划中标明每项能力需要单遍、重复读取还是全量物化。
- 为频次、对象去重、违规样本、预览和深度分析分别设置预算。
- 明确预算超限后的行为：报错、近似算法、截断或磁盘暂存。
- 提供统一的精确度与截断元数据，描述哪些结论基于完整数据、哪些是估计。
- 对可合并草图优先采用单遍计算，减少因导出需求重复读取数据。

### 验收标准

用高基数字段、大量重复组和大文件验证资源上限。报告能够解释近似与截断，不能将受限样本的结论表达成精确全量结果。

## 7. 建立统一的结果投影与脱敏出口

### 当前问题

报告和脱敏代码需要手工复制或透传结果字段，新结果属性容易在某个出口遗漏。除频次外，重复对象、模糊聚类、默认值、违规样本和嵌套结构也可能携带原始值，需要统一检查。

### 建议改造

- 建立统一结果访问或投影机制，集中定义结果成员及其原始值位置。
- 各宿主、报告导出和预览共用脱敏策略与结构化路径解析。
- 递归处理对象、数组与特殊属性名，并覆盖不同标量类型。
- 明确原始计算结果与用于展示、分发的投影，避免在原结果上就地修改。
- 同一投影集中生成展示值、类型和计数，减少宿主各自转换。
- 对不支持安全转换的原始值载体明确报错或隐藏，避免无声透传。

### 验收标准

新增结果属性能被出口完整性检查发现。敏感值在频次、预览、重复对象、模糊聚类和违规样本中均按策略处理；脱敏幂等，且不改变原始分析结果。

## 8. 重构 Schema 推断与导出模型

### 当前问题

已有共享的 Schema 树，但节点仍同时保存 C#、TypeScript、JSON Schema 等目标类型。数组索引归并、混合类型、null、字段缺失和目标语言命名规则需要进一步独立建模。

### 建议改造

- 建立与目标语言无关的类型图，描述值类型集合、对象属性、数组元素、数值范围和精度。
- 将可缺失、可为 null、空数组和未知元素类型分别表示。
- 同一数组不同索引的类型证据统一合并，避免遍历顺序影响结果。
- 将类型推断、标识符分配和目标代码生成分成独立步骤。
- C#、TypeScript、JSON Schema、OpenAPI、Protobuf 和 SQL 通过各自后端消费同一类型图。
- 目标格式不能表达某种语义时，输出明确诊断和回退策略。

### 验收标准

调换记录与属性顺序后推断一致。覆盖异构数组、嵌套数组、空对象、空数组、特殊属性名和命名冲突；生成代码通过适合对应语言的验证。

## 9. 拆分计算内核、基础设施和平台业务

### 当前问题

Core 当前同时包含统计、数据库驱动、Excel/PDF 导出、密码处理、SQLite 存储、作业生命周期和告警业务。只复用统计功能也会引入较大的依赖集合。

### 建议边界

以下是候选职责边界，项目名称在实施时确定：

| 模块 | 职责 |
|---|---|
| Core | 值与路径、统计状态、规则、类型推断、结果模型 |
| Application | 分析用例、阶段编排、运行事件与输入输出端口 |
| Parsing / Adapters | 文件格式、压缩、数据库连接与第三方输入依赖 |
| Exporting | 各报告和目标代码输出，承载 PDF、Excel、Roslyn 等依赖 |
| Infrastructure | SQLite 存储、外部密钥服务和其他 IO 实现 |
| Platform | 作业、历史、质量基线、责任、修复与告警业务 |

先完成接口和职责分离，再移动到独立项目。保持依赖单向，领域计算不引用具体存储或宿主。

### 验收标准

新建一个只做内存记录统计的应用时，可以只引用计算内核；无需引入数据库驱动、PDF 或作业平台。CLI、API、Web 和 Desktop 通过组合根接入所需模块。

## 10. 建立统计契约测试与性能基线

### 当前问题

已有较多功能回归测试，但重构还需要验证跨分块、跨线程与恢复后的统计一致性。资源与性能变化也应通过固定数据集测量。

### 建议改造

- 增加状态合并性质测试：空状态、分块、不同合并顺序，以及明确误差范围内的并行一致性。
- 为值模型和路径增加生成式测试，覆盖特殊字符、深层结构、数字边界和序列化往返。
- 以小型确定性数据集验证精确指标，以已知误差标准验证草图。
- 建立 BenchmarkDotNet 基准，记录吞吐、分配、内存及不同并行度表现。
- 建立固定跨格式样例，验证各数据源归一化后语义一致。
- 修复 SQLite 测试的连接池与临时文件清理隔离，使基础回归保持稳定。
- 采用文档化的快照版本和公开 API 兼容性策略。

### 验收标准

每次重构具备可重复的正确性证据；涉及性能目标的改动给出相同环境、数据与配置下的前后对比。基准用于识别变化，不依赖易波动的单次计时断言。

## 每项实施的完成条件

1. 新职责和公开契约清晰，必要的宿主适配同步完成。
2. 删除被替代的重复实现，兼容适配层具有明确用途。
3. 针对实际风险补充测试，完整解决方案构建通过。
4. 记录序列化、快照和配置的破坏性变更及迁移方式。
5. 以一个独立、可审查的主题提交；实施下一项前更新本文状态。
